# Creative Direction V2 — implementation roadmap

**October 10, 2026 · America/New_York · Planning only**

[Creative authority](CREATIVE_DIRECTION_V2.md) · [Evidence and scope](V2_RECONCILIATION.md) · [Deployment gates](DEPLOYMENT_GATES.md)

This replaces incompatible future work in the Gatehouse G1–G3 and external M0–M9 design roadmaps. Already implemented G1 and M0–M2 remain baseline evidence, not tasks to repeat or authorization to expand. The latest owner brief authorizes Phase 0 documentation only.

## Phase 0 — Direction and documentation

- **Goal:** reconcile the current dirty working tree with V2 without changing experience code.
- **Deliverables:** source-grounded creative/IA/visual/interaction specification, preservation matrix, ten decision positions, decision register, roadmap and scoped reconciliation record; clear supersession links in older entry documents.
- **Dependencies:** current owner brief, actual source/doc inspection and existing canonical references. Original concept #3 image is unavailable and explicitly bounded.
- **Acceptance:** current versus proposed behavior is distinguished; two paths, domain ownership and engineering invariants are explicit; historical evidence remains labeled; runtime/asset/legacy hashes unchanged by this phase.
- **Risks:** contradictory authority, accidental edits to pre-existing work, old passes presented as new.
- **Approval:** present package and stop. No runtime approval is inferred. Status: documentation prepared; verification is recorded in the reconciliation record.

## Phase 1 — Design validation

- **Goal:** prove the composition and operator relationship before scaling or replacing working scenes.
- **Deliverables:** proposed desktop 1920×1080/1440×900 and mobile 390×844/320 layouts; static/reduced-motion variants; asset needs and loading plan; one isolated signal-artifact proof with Human exit only if separately authorized. Start from the existing Gatehouse, not a new foundation.
- **Dependencies:** owner approval of R1–R3 direction and explicit scope to create mockups/prototype; canonical references already available. No new route or final artwork is prerequisite.
- **Acceptance:** owner can review a concrete composition; unfamiliar visitors can identify Deffy, Defdef's job, Projects/Human/Worlds and the anomaly's role; all ordinary links work without the encounter; static/mobile layouts communicate the same identity. Record observed visitor feedback, not invented success rates.
- **Risks:** front-desk bureaucracy, underwhelming spectacle, confusing character/persona names, unseen concept imitation, mobile crowding.
- **Approval:** explicit authorization before prototype code or scene changes. Owner visual acceptance of the proof before replacing the production-source homepage composition. Mockup approval alone does not authorize implementation.

## Phase 2 — Experience architecture

- **Goal:** prepare only the seams demonstrated by the approved proof.
- **Deliverables:** bounded domain/component interface, typed optional artifact record if necessary, navigation priority plan, native disclosure/static fallback, small event lifecycle if justified; migration checklist for legacy `/#meet` and identity copy.
- **Dependencies:** approved Phase 1 result and explicit implementation scope. Retain installed Astro and existing directory routes.
- **Acceptance:** initial HTML contains every required destination and content; controller can be absent; storage failure, rapid activation and preference changes remain safe; no client router, game engine, new renderer or backend; route manifest and publication validator retain their contracts.
- **Risks:** abstractions larger than the encounter, archive data pulled into public models, hidden navigation dependence.
- **Approval:** included only within an expressly authorized implementation phase. New owned routes, rendering dependencies or weakened safeguards require a documented reason and explicit owner approval; they are not recommended defaults.

## Phase 3 — Incremental scene implementation

- **Goal:** integrate one V2 encounter at a time while preserving a usable baseline.
- **Deliverables:** approved arrival refinement, bounded Defdef domain, clear Human transition; later artifact/world visual refinement independently. Keep unused Hero/Meet source and existing canonical assets until any retirement is separately reviewed.
- **Dependencies:** accepted composition and architecture; reviewed runtime derivatives for any new pose/art. Use current static canonical derivative first.
- **Acceptance:** each slice has one clear authorial purpose, complete express path and static fallback; no lore/biography invention, no unapproved archive export; protected namespaces remain untouched; existing project status and filter/history behavior survives.
- **Risks:** reverting to mascot tour guide, red leaking into global style, perpetual effects, compulsory long homepage, duplicated human copy.
- **Approval:** explicit scene-change authorization after direction review; each materially expanded slice must fit agreed scope. Scene acceptance is separate from release authorization.

## Phase 4 — Integration and refinement

- **Goal:** verify the whole selected experience, pacing and failure behavior against a frozen candidate.
- **Deliverables:** source/type/publication/output checks; browser journeys; rendered contrast; responsive captures at 1920/1440/768/390/320, text enlargement; keyboard/manual screen-reader and physical Android/iOS evidence; cold-load transfer/memory/interaction and long-task reports; reviewed copy/provenance.
- **Dependencies:** selected Phase 3 scope, reproducible local preview and approved content. Optional photos/tracks/archives may remain deliberately absent.
- **Acceptance:** preserved budgets in creative spec met under recorded profiles, no unexplained decorative long-task breach, equal static/animated content, direct deep links, Back/new-tab and failures work; content accurate; no inaccessible effects or private output. Lab results are not field p75/INP. Mark PASS/FAIL/NOT RUN/BLOCKED explicitly.
- **Risks:** desktop-only confidence, inherited tests asserting outdated identity meaning, font/layout long tasks, tests passing while operator story remains unclear.
- **Approval:** owner visual/content acceptance; missing mandatory device/manual evidence is disclosed and assessed before release, not silently waived by automation. Budget changes require documented explicit approval.

## Phase 5 — Release readiness

- **Goal:** prepare a reversible, scoped candidate for separate publication approval.
- **Deliverables:** authoritative production backup and manifest; publisher/route ownership proof; `/story` slash/alias resolution plan; staging rehearsal, cache/worker compatibility, retained-app verification, exact per-file release manifest and rollback rehearsal; selected-content approval and indexing plan.
- **Dependencies:** Phase 4 acceptance plus verified origin/publisher, host capabilities and restoration path. Local legacy integrity baseline is not a production backup.
- **Acceptance:** every deployment gate satisfied or explicitly unresolved; old `/projects/story/` and `/storytime` survive; new `/story/` loads correctly; music and product privacy namespaces retained; no private authoring/docs/masters ship; restore actually demonstrated.
- **Risks:** non-atomic upload, stale workers, redirect precedence, whole-tree overwrite, production drift, premature indexing.
- **Approval:** separate explicit staging/upload authorization and final publication authorization as applicable. No deployment or live hosting changes are authorized by this roadmap. Preserve noindex until an approved launch change; never use destructive synchronization.

## Recommended first implementation slice — after authorization

Authorize **one isolated Defdef-domain proof based on the existing Gatehouse**. Deliver a desktop/mobile static composition, one native signal-artifact disclosure, one bounded optional response using current art or a reviewed supplied still, and an immediate `/story/` exit into the existing quiet introduction. No new route, dependency, audio, archive content, full catalog or asset replacement.

Success is visitor understanding of ownership and cause/effect, plus usable express navigation with JS/motion absent. Validate the proof's changed behavior and output budgets; review it with the owner before integration. Do not rebuild G1, repeat the entire historical M0–M2 program, or scale six conceptual zones into scenes before this proof earns its place.

**Dependency chain:** Phase 0 review → authorized Phase 1 proof → accepted composition → authorized Phase 2/3 integration → Phase 4 evidence → Phase 5 release review → separately authorized publication. Today stops at Phase 0.
